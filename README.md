# Drover

Drover는 OpenStack 환경에서 K3s 클러스터와 노드그룹의 lifecycle, 내구성 operation/job, OpenStack inventory reconciliation을 제공하는 control plane 서비스입니다.

- 현재 구조와 변경 시 갱신 규칙: [ARCHITECTURE.md](ARCHITECTURE.md)
- API 및 운영 문서 색인: [docs/README.md](docs/README.md)
- 패키지·실행 진입점: [pyproject.toml](pyproject.toml)
- CI 계약: [.github/workflows/ci.yml](.github/workflows/ci.yml)

문서 또는 코드 변경 전 `ARCHITECTURE.md`를 읽고, 변경 후 source를 다시 검토한 다음 다음 명령으로 architecture snapshot을 확인합니다.

```bash
python3 scripts/check_architecture.py
```

## Package and Kolla role

The root `drover` wheel owns the Python package and the Kolla-Ansible role as wheel shared data. Installing the wheel places the role at `share/kolla-ansible/ansible/roles/drover` under the installation prefix; it does not install Kolla-Ansible or service runtime dependencies.

Use the `service` extra to run the API, worker, or migration entry points locally:

```bash
uv sync --extra service --extra dev --frozen
```

Build the distributable root wheel with `uv build --wheel`. Container builds use the repository-root context and `docker/Dockerfile`:

```bash
docker build --file docker/Dockerfile --target drover-api .
```

## Requester execution and cluster resource credentials

**Published 0.4.4 patch — execution-authority cutover; locally verified, not live-verified.** The recorded 2026-10-07 local evidence (OpenSpec `isolate-service-execution-credentials` task 4.4) is the full non-integration suite (1123 passed / 1 skipped), SDK `tests/test_proxy.py` (114 passed), the real-SDK loopback trust test and a disposable MariaDB 11.4 001–004 ledger run. Final integrated qualification and immutable tag/image/wheel publication are recorded separately in the release notes; no live Keystone/OpenStack/K3s checks, credential rotation or production cutover have been performed for this model. See the [0.4.4 patch section](docs/release-0.4.0.md#044-patch).

Durable create/scale/delete and manual nodegroup mutations use a per-operation requester-owned Keystone trust (`impersonation=True`, Drover service-project identity as trustee). Only currently held configured required/optional roles are delegated; never `admin` or `manager`. Each connection revalidates principal, project, exact operation capability, held roles and token scope/expiry; all admitted role IDs must be present in the token, Keystone implied roles are allowed, and `admin`/`manager` token roles are rejected. Revoked/missing/mismatched/exhausted authority is terminal; directory/Keystone outages use attempt-fenced retry, never another identity. Callback/HA/agent continuation uses the admitted create trust. Idle trusts become `released`; after each job and during the 300s sweep, released/revoked trusts are DELETEd through their own impersonating trust-scoped password token with no project selector. Success/404 records `deleted`; Unauthorized/Forbidden records `trust inert until expiry` without changing released/revoked state; outages retry on the next sweep. Expired rows require Keystone GET 404 before `expired`. TTL remains a fallback bound, not the normal completion-cleanup path. Caller tokens/passwords are not persisted. Tenant manager users, stored manager-password execution and manager application-credential creation are removed.

Create admission separately issues caller-owned restricted (`unrestricted=False`) **control** credentials for Drover and **guest** credentials when OpenStack plugins need them; secrets are encrypted in the DB. Control never enters guest config. Stampede revalidates the owner’s current scale capability; reconciliation/health use get. Legacy clusters require reauthorization and cannot enable Stampede without active control authority.

- `conn.drover.cluster_authorization(id)` → secret-free generation/state/owner-revocation backlog.
- `conn.drover.reauthorize_cluster(id)` → POST `/v1/clusters/{id}/authorization`, 202 with operation/job ID; only ACTIVE clusters with no competing mutation. Poll completion, not merely admission.
- Guest rollout replaces cloud-config/Manila Secret and Octavia Ingress ConfigMap credential keys, restarts referencing kube-system workloads and waits for rollout. KMS/legacy detection runs control-plane host Jobs with `nsenter` to rewrite `/etc/kubernetes/barbican-cloud.conf` and existing `cloud.conf`, restart `barbican-kms.service` and check its socket. A final Secret-write probe precedes atomic activation. Partial failure keeps the old active generation and staged error; already changed guest objects are not guaranteed to roll back.
- `conn.drover.retire_cluster_credentials(id)` → owner-token deletion of caller-owned retiring credentials. Activation erases superseded secrets, but other-owner/legacy remote revocation remains reported. Durable deletion uses the current authorized delete actor, independently of the creator; current tenant delete-async instead uses the caller connection directly and is not a durable trust job.

Afterglow provisioning intents are removed. Drover creates native GPU workers itself and re-checks configured GPU admission before every new create; admission counts live usage, not reserved capacity. Remove Settings/Kolla `drover_afterglow_provisioning_url`, `drover_afterglow_provisioning_token`, `drover_afterglow_provisioning_token_file` and `DROVER_AFTERGLOW_PROVISIONING_TOKEN_FILE`. Kolla removes the `afterglow_k3s_provisioning_token` file; GPU admission configuration/files remain.

New `[drover]` settings (Settings/Kolla use `drover_` prefix): `operation_trust_ttl_seconds=14400`, `operation_trust_min_remaining_seconds=300`, `delegated_required_roles=["member"]`, `delegated_optional_roles=["load-balancer_member"]`, `guest_rollout_timeout_seconds=600`. Required roles must be nonempty; optional roles are only delegated when held. Barbican member and Octavia member-role policy sufficiency are **[INFERENCE]**, not live-verified.

Upgrade in order: **apply 004 → drain pre-upgrade mutation/callback jobs with the old worker → cut over API/Worker → reauthorize legacy clusters and complete guest rollout → remove `afterglow-cluster-mgr-*` users/old credentials out of band**. See the [migration runbook](drover/migrations/README.md#execution-authority-upgrade-004), [API reference](docs/drover-api-v1-reference.md), and [architecture authority/Keystone limits](ARCHITECTURE.md#execution-authority와-재인가-source-reviewed-live-verified-아님). Keystone master's [trusts.py](https://github.com/openstack/keystone/blob/master/keystone/api/trusts.py) `_check_delegated_token` does not block ordinary trust-scoped tokens; `identity:delete_trust` allows the trustor represented by an impersonating token, which Drover uses for trust cleanup. [Users.py](https://github.com/openstack/keystone/blob/master/keystone/api/users.py) still blocks trust/OAuth/EC2 app-credential management and restricted app credentials from managing additional credentials, so resource-credential retirement requires the owner's non-delegated token. `tests/test_native_trust_loopback.py` defines real keystoneauth1/keystoneclient HTTP create/project-less OS-TRUST authentication/delete and revoked-role denial against a synthetic provider: **test-defined**, not live-cloud evidence or a test run by this documentation slice.


## Native scoped access and credential smoke

**Scoped service grades — published in the 0.4.4 patch.** Preserve project/core role IDs and assignments; `drover_editor` permits cluster create/update and isolated workload use, `drover_user` only reduced read-only access, and destructive/full-certificate actions require distinct administrator leaves. The immutable tag is published; production cutover is held pending project/user service-grade review. Final integrated regression selectors passed 69 tests and the full native suite passed **1,037 tests / 3 skipped** at that slice. The actual two-architecture Kubernetes acceptance and its image/PATH, token-expiry, synthetic-directory and queue-only deletion limits are recorded below; those limits are not waived by the test counts.


Native APIs require validated Keystone project identity and **fresh effective assignments plus the actual role-ID inference graph**, not caller-supplied role headers or hardcoded parent expansion. Preset `drover_reader/user/editor/admin` names describe initial hierarchy links only: deleting a parent-to-leaf link revokes that feature on the next request. Authorization accepts exact uniquely resolved global leaf IDs/names (`drover-inventory_reader`, `drover-access_user`, `drover-clusters_editor`, `drover-workloads_editor`, `drover-clusters_admin`, `drover-access_admin`); same-name domain aliases confer no authority. Inventory requires effective base `reader` or `member`; use/write/admin require effective base `member`. Project owner/admin/member/reader alone grants no Drover entitlement. Nonverified raw `admin`/`manager` principals fail closed. Global settings, resource policies and template management remain verified system-admin only; service admin never becomes OpenStack/system admin. Directory/graph failures deny without falling back to embedded token roles. Callback token/CIDR authentication is independent.

Reduced-grade download uses ServiceAccounts, explicit Kubernetes RBAC and TokenRequest, never the stored client certificate/key with an impersonation marker. Tokens last at most 900 seconds and cannot outlive the validated Keystone token. Because Kubernetes requires a minimum 600-second request, sessions with less remaining time must reauthenticate. Provider overlong/invalid expiration fails closed. Downloads are `no-store`; HEAD is authorization/metadata-only and neither decrypts nor issues credentials. Response headers identify expiration and the editor workload namespace. Shell always receives an expiring restricted workload kubeconfig, including when started by an administrator.

`GET/HEAD /v1/clusters/{id}/kubeconfig?grade=user|editor|admin` selects the exact requested variant. Default is **user**, even for access administrators; full stored certificates require explicit `grade=admin`. User grade requires access-user or access-admin, editor grade workload-editor or access-admin, admin grade access-admin (plus base member; verified system-admin bypass is separate). Unauthorized requested grades return 403 without fallback or silent downgrade; unknown grades return 422. Restricted GET responses carry `X-Credential-Expires-At` and `X-Workload-Namespace`; full administrator responses deliberately have no bearer expiry header. HEAD never issues credentials and does not establish issuance readiness.

Editor namespaces are deterministic per project/user, separate from `afterglow-shell` and `drover-credentials`. Editor issuance needs Kubernetes **1.30+** with stable `admissionregistration.k8s.io/v1` ValidatingAdmissionPolicy and Pod Security Admission enabled. The issuer installs a restricted pod-security namespace plus fail-closed admission rejecting elevated service accounts, mounted credentials/secrets, projected token volumes and secret environment references. Editor RBAC does not grant RBAC, service-account, namespace or secret/token administration. ConfigMap/Secret native APIs are not reader inventory and require workload/admin authorization; editor secret writes are Opaque-only in the isolated namespace. Existing arbitrary application namespaces require a project access administrator.

`GET /v1/clusters/{id}/namespaces` for editors without access-admin prepares the private workload namespace and verifies its admission boundary, then returns only that usable namespace. It does not mint/discard a token. Other inventory readers receive namespace metadata; access administrators receive the full list. Shell/exec accepts workload-editor or access-admin because full project-cluster credentials already carry Kubernetes workload authority; the shell mount remains restricted for both. Nodegroup deletion requires cluster-admin, while create/update/scale requires cluster-editor.

The stored administrative kubeconfig must contain its server CA and a reachable TLS endpoint for issuance. The API needs Kubernetes authority to reconcile the issuer ServiceAccount, RBAC and admission resources and create TokenRequests. The optional Keystone authentication webhook templates are **not** used as a substitute for issuance, and enabling authentication alone does not grant restricted authorization.

Installing a node SSH key during cluster creation also requires `drover-access_admin`, because node SSH can read K3s's administrator certificate. These are Drover/Kubernetes API boundaries, not a restriction on independently granted Nova, hypervisor or host-root permissions; operators must secure those external control planes separately.

### Historic credentials and revocation limits

Policy changes cannot recall previously downloaded administrator certificates or copies from historic shell PVCs/secrets. Removing `as` from those old configs exposes their underlying administrator identity. Operators must inventory that exposure and explicitly plan trust/CA remediation or cluster replacement; ordinary rolling leaf-certificate renewal is not a claim of revoking copied certificates. This change performs **no live credential rotation**, cluster mutation or deployment. Legacy shell pods are replaced on use rather than trusted with a new marker; historic copies still need operator remediation.

Roles embedded in already-issued Keystone scoped tokens may remain stale, so Drover independently queries current effective project assignments, unique global role IDs and the actual inference graph at every native authentication. It does not use token introspection alone as a fresh assignment check. Removing an assignment or graph edge affects the next native request, subject to Keystone's own consistency. Already-issued Kubernetes bearer tokens remain valid until their bounded expiration after a downgrade; this is not instantaneous Kubernetes revocation.

### Native runtime smoke

Use Python 3.12 and `uv sync --extra service --extra dev --frozen` in this repository. After integration, run:

```bash
uv run --frozen pytest tests/test_policy.py tests/test_auth.py tests/test_current_role_directory.py tests/test_scoped_api.py tests/test_scoped_credentials.py tests/test_k3s_kubeconfig_audit.py tests/test_k3s_shell.py tests/test_k3s_cloud_shell_service.py

```

`test_scoped_credentials.py` exercises the native FastAPI download path with synthetic Keystone validation, an ephemeral localhost Kubernetes HTTP boundary, real httpx RBAC/TokenRequest issuance requests, and the returned bearer token against the boundary's permission checks. It checks read allowed/create-delete denied, editor namespace isolation, no certificate/key export, expiry and provider failures. Shared tests use fakeredis and in-memory boundary records, not production MariaDB/Keystone/Kubernetes. This smoke is a behavioral boundary test, not evidence that a real Kubernetes API server evaluated RBAC/admission CEL. Real-cluster acceptance additionally requires a disposable 1.30+ cluster and verification of `kubectl auth can-i` plus denied privileged/credential-mount pods using issued editor credentials; never use a production cluster for that smoke.

**Disposable real-cluster smoke (2026-10-07, local only).** The working-tree `drover-api`/`drover-worker` targets were built for `linux/amd64,linux/arm64` with `docker buildx build --platform linux/amd64,linux/arm64 -f docker/Dockerfile --target <target> --load .` and imported/executed on both architectures. The API image then ran its canonical `uvicorn` command against a disposable MariaDB 11.4 (migrated with the image's `drover-migrate --apply`), Redis 7 and a disposable `rancher/k3s:v1.31.4-k3s1` container; the stored project kubeconfig was that k3s cluster's own admin kubeconfig, written through the real encrypted store. Only Keystone was synthetic (an HTTP v3 boundary driven through the image's keystoneauth/keystoneclient, with mutable assignments and inference edges). A driver checked 119 outcomes against both the arm64 and amd64 API containers, 119/119 each. These covered reader/user/editor/admin/system-admin grades; raw project `admin`, domain-scoped aliases and system-assignment rows with the wrong user, role or scope; and cross-project access and rescope. With issued bearer tokens, the real apiserver allowed read-only access to user grade and denied secrets, mutation, exec, node/namespace deletion and cluster-role binding. Editor grade could write and exec only in its namespace. Denied there: secrets, other namespaces, RBAC, ServiceAccount tokens, node/namespace deletion, secret-volume pods (the real ValidatingAdmissionPolicy denied them) and privileged pods (PSA). Admin grade worked only for explicit access-admin or verified system admin. The run also covered the Cloud Shell ticket/WebSocket session, where the shell pod's `kubectl auth can-i` matched the editor boundary and its kubeconfig was token-only. Edge removal, unassignment and system-role revocation each took effect on the next request with an unchanged Keystone token. This proves local semantics only: no OpenStack, production Keystone, production cluster or deployment was used.

The first editor issuance on a fresh cluster exposed that a newly applied ValidatingAdmissionPolicy/binding is not enforced immediately: k3s admitted the dry-run probe once or twice (~1 s) before denying it. Issuance now repeats the dry-run probe up to `ADMISSION_PROBE_ATTEMPTS` (20) at `ADMISSION_PROBE_INTERVAL_SECONDS` (0.5 s) and still fails closed with 502 if the binding never enforces. Cloud Shell prerequisites observed in that run: the default `bitnami/kubectl:1.31` tag is no longer resolvable from Docker Hub (the smoke re-tagged `bitnamilegacy/kubectl:1.31` under that name inside the disposable node only). In that image the login shell also resets `PATH`, so `kubectl` lives at `/opt/bitnami/kubectl/bin/kubectl` but is not on the shell's default path. Clusters need a mirrored shell image, and users currently need the full path.
