## Context
Before this change every worker connection came from `services/keystone.py:get_project_manager_connection`: the service account (admin on `drover-service`) created `afterglow-cluster-mgr-<project>`, assigned it `member` and `load-balancer_member` on the tenant project and stored its password (`project_manager_credentials`). Provisioning, autoscale, deletion, reconciliation, health probes, Barbican KEK creation, HA callbacks and per-cluster application credentials all used it. Jobs stored only actor labels, so revocation never reached queued or continuous work, and the Stampede actor (`stampede-system`) carried no human authority.

Keystone source facts used here (openstack/keystone master and stable/2025.2, read 2026-10-07): trust-scoped and other delegated tokens cannot create, list, read or delete application credentials (`api/users.py:_block_delegated_token_app_creds`); `api/trusts.py:_check_delegated_token` blocks application-credential, OAuth1 and EC2 tokens from trust management but deliberately does NOT block trust-scoped tokens, and `identity:delete_trust` allows admin or the trustor, so an impersonating trust-scoped token (whose user is the trustor) may delete its own trust; Keystone expands implied roles into trust and application-credential tokens; restricted application-credential tokens may read but not create/delete application credentials; Keystone deletes a user's application credentials when the user is deleted/disabled or loses a project assignment (`application_credential/core.py` callbacks). Installed SDKs: keystoneclient 5.4 `TrustManager.create(trustee_user, trustor_user, role_ids, project, impersonation, expires_at)`, keystoneauth1 5.15 `AccessInfoV3.trust_id/trustee_user_id/trustor_user_id/role_ids`, openstacksdk 3.3 `identity.create/get/delete_application_credential(user, ...)`.

## Goals / Non-Goals
Goals: no tenant manager users or role assignments; every tenant mutation runs under admitted, revalidated, least-privilege requester authority; continuous work runs under explicitly approved user-owned restricted application credentials; operators can reauthorize new or legacy clusters with real guest rollout; deletion never depends on the original creator.

Non-goals: changing native Kubernetes RBAC/TokenRequest issuance, removing existing tenant manager users or role assignments in production, Keystone/Nova policy changes, rotating historic downloaded certificates.

## Decisions
1. **Operation Trust admission (`services/delegation.py`).** API routes that enqueue create, delete, manual scale or nodegroup jobs authorize the exact Drover action, read the caller's current effective global role IDs (the same uncached directory graph as native auth), and create a trust with the caller's validated scoped token: trustor = caller, trustee = Drover service user resolved from service-project authentication, project = token project, `impersonation=True`, `role_ids` = configured required roles (default `member`) plus configured optional roles (default `load-balancer_member`) that the caller actually holds, `expires_at = now + drover_operation_trust_ttl_seconds` (900–86400, default 14400). `admin`/`manager` cannot be configured. The returned trust is verified field by field. The admitted reference is persisted in `drover_delegations` in the same transaction as the job (`drover_jobs.delegation_id`). If no job is persisted, the API deletes the trust with the caller token (allowed, trustor non-delegated); if the process dies first, finite expiry bounds it.
2. **Worker execution authority (`services/execution.py`).** `jobs._execute_job_direct` binds exactly one authority per job via a context variable: an operation authority for create/bootstrap_ha/provision_agents/scale/manual nodegroup/delete, a resource authority for Stampede jobs and reconcile, none for certificate rotation and reauthorization rollout. Service code calls `execution.open_connection(project_id)`/`execution.connection(project_id)`; with no bound authority or a project mismatch it fails closed. Legacy queued mutation jobs without `delegation_id` fail terminally.
3. **Per-connection revalidation.** Before every trust connection Drover reloads the delegation, checks state/project/cluster/kind compatibility and remaining lifetime (`drover_operation_trust_min_remaining_seconds`), re-reads the trustor's enabled user and project, recomputes current roles and system-admin status, enforces the stored action through `policy.authorize`, requires the delegated roles still be held, then authenticates `v3.Password(user_id=trustee, password, trust_id)` without project selectors and verifies trust scope, project, impersonated user, trustor/trustee, role subset and expiry. Revocation/mismatch raises `AuthorityRevoked` (terminal, delegation marked `revoked`, no retry); directory/Keystone transport faults raise `ExecutionAuthorityUnavailable` and keep normal retry semantics. Lease and attempt fences are unchanged.
4. **Continuations.** The callback copies the create operation's active delegation to `bootstrap_ha`/`provision_agents`; the HA joiner LB member uses it inline; the callback-timeout rollback delete may use the create delegation only when `expired_operation_id` equals the delegation's operation. Release: when a job finishes and no queued/running job references its delegation and the operation is no longer queued/running/waiting, the delegation becomes `released`. Right after the job (and on every 300 s sweep) Drover deletes released or revoked trusts through their own impersonating trust-scoped token (`deleted`; 404 = already gone); if Keystone refuses that token because the trustor lost roles, the trust is unusable and stays recorded as inert until its finite expiry, after which the sweep records `expired` once the trustee no longer sees it. Outages retry on the next sweep. Cleanup failure never repeats cloud mutation. Token verification requires the delegated role IDs to be present (Keystone adds implied roles) and rejects any token carrying admin or manager.
5. **Resource authority (`services/cluster_authority.py`).** Each generation has a `control` credential (Drover only) and, when OCCM/Manila CSI/Octavia Ingress/Barbican KMS are active, a separate `guest` credential. Both are created synchronously with the operator's own token (Keystone forbids delegated tokens), are restricted, carry only the delegated role subset, have no expiry (resource lifetime, user-approved) and are verified (project, restricted flag, roles). Secrets are AES-GCM encrypted in a new `cluster_app_credential` domain. Before each control use Drover revalidates the owner's enabled user/project and capability (`drover:clusters:scale` for Stampede jobs/decisions, `drover:clusters:get` for reconcile/health) and verifies the application-credential token (project, user, credential ID, roles). Missing authority raises `ReauthorizationRequired`; Stampede records `reauthorization_required`, reconcile scheduling skips the cluster, enabling Stampede returns 409.
6. **Reauthorization (`api/authorization.py`, `services/guest_rollout.py`).** `POST /v1/clusters/{id}/authorization` (new `drover:clusters:reauthorize`, default clusters admin) requires an ACTIVE cluster without other mutation jobs, creates staged control/guest credentials for generation N+1, persists them and enqueues `reauthorize` (operation kind added in migration 004). The job revalidates the operator, authenticates both staged credentials, and for guest credentials replaces only the application-credential keys in `kube-system/cloud-config`, `manila-cloud-secret` and the Octavia Ingress ConfigMap (objects absent from the cluster are skipped), restarts every kube-system Deployment/DaemonSet/StatefulSet referencing them and waits for rollout, and on each control-plane node runs a host Job that rewrites `/etc/kubernetes/barbican-cloud.conf` (and stale `/etc/kubernetes/cloud.conf`) through `nsenter`, restarts `barbican-kms` and waits for its socket, then probes a Secret write. Only after full success one transaction activates N+1 and moves the previous active generation, older staged generations and an untracked legacy `app_credential_id` to `retiring` with ciphertext erased. Until then all earlier credentials remain valid, so a partial or failed rollout leaves a working cluster and a retry or newer generation converges.
7. **Retirement and deletion.** Drover can delete only credentials owned by the caller of a synchronous request. `POST /v1/clusters/{id}/authorization/retire` deletes caller-owned retiring credentials; reauthorization admission and DELETE admission opportunistically delete caller-owned retiring/obsolete credentials. A durable delete job (trust) cannot delete application credentials; it erases all remaining ciphertext and marks them `retiring` with reason `owner_revocation_required`. Credentials of departed owners are removed by Keystone itself.
8. **Removals.** Manager user creation/assignment/password use, `get_project_manager_connection`, `project_manager_connection`, manager app-credential helpers, `auth.get_admin_connection_for_project`, manager password crypto and cutover manager-password decryption. The historical `project_manager_credentials` table stays (immutable baseline) and is copied byte-for-byte by cutover for operator cleanup only.

## Risks / Trade-offs
- Trust and resource credentials require the caller to hold `member` on the project; projects relying on manager-only roles will fail closed. Octavia/Barbican project-member defaults are assumed and documented as [INFERENCE] until live verification.
- A failed or aborted rollout keeps staged credentials until a newer reauthorization succeeds; retiring credentials owned by another present user remain valid in Keystone until that owner retires them or loses access; the API reports them.
- Existing clusters lose continuous authority (Stampede/reconcile/health floating-IP probing) until reauthorized; manual operations still work through per-operation trusts.
- Upgrade must drain mutation jobs queued before migration 004, otherwise they fail terminally by design.

## Migration Plan
Apply `004_execution_authority.sql` (new tables, nullable job column, widened operation kind check). Deploy API and worker together. Reauthorize every existing cluster as a current clusters admin, confirm `GET /authorization` shows active control (and guest when plugins exist), then remove legacy `afterglow-cluster-mgr-*` users out of band (Keystone deletes their application credentials). Rollback: previous images ignore the new tables; manager rows were never deleted.
