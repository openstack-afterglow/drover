# Staging verification boundary

The repository validates unit behavior locally. The `Manual Live OpenStack Gate` workflow is `workflow_dispatch`-only and is excluded from push, pull-request, and post-CI automation. It verifies a separately deployed live Drover service; it does not install or reconfigure Kolla from a GitHub-hosted runner. Live checks require `DROVER_INTEGRATION_CLOUD=1` and the GitHub `staging` environment:

- The manually requested revision is checked out exactly, while concurrency prevents overlapping cluster lifecycles.
- Root `drover` wheel installs the role at `share/kolla-ansible/ansible/roles/drover` beneath the selected Python prefix. Its base install deliberately has no Kolla-Ansible or service-runtime dependencies; install the `service` extra only when this environment runs Drover processes.
- The workflow validates the role source at `deploy/kolla/ansible/roles/drover`; release CI separately builds, installs, and uninstalls the root wheel to prove the shared-data ownership.
- A dedicated project, network, subnet, image, flavor, volume availability zone, and external network must be configured for disposable tests.
- Drover resource policies must be pinned to those staging resources, including the HA load-balancer subnet, and `k3s.version` must be configured.
- A one-master lifecycle exercises create, scale, inventory, delete, and fail-closed cleanup.
- A three-master lifecycle verifies Nova, Cinder, Neutron, and Octavia inventory before delete and cleanup.

The workflow requires HTTPS `OS_AUTH_URL` and `DROVER_API_URL`, `OS_USERNAME`, `OS_PASSWORD`, `OS_PROJECT_NAME` or `OS_PROJECT_ID`, `DROVER_INTEGRATION_NETWORK_ID`, `DROVER_INTEGRATION_SUBNET_ID`, `DROVER_INTEGRATION_IMAGE_ID`, `DROVER_INTEGRATION_FLAVOR_ID`, `DROVER_INTEGRATION_EXTERNAL_NET_ID`, and `DROVER_INTEGRATION_VOLUME_AZ`. Credentials must be scoped to the isolated staging project and carry the Drover admin policy required by the gate's `admin_managed_resources` and `admin_cluster` inventory/cleanup assertions, in addition to the current native create/scale/delete capabilities and all configured required delegated roles. Holding admin authority for these assertions is not delegation of admin: only the configured held required/optional roles enter a trust or cluster credential, and Settings/Kolla reject `admin`/`manager` in those role lists. Admin API access still does not permit a cross-project mutation token; trust-admitted create/scale/delete calls require the target-project requester token.

Local readiness smoke proves database, Redis, and migration-ledger readiness. It deliberately reports `503` while Keystone is unavailable; a `200` readiness response requires reachable configured Keystone service credentials.

Native Kolla enables Drover Sentinel discovery by default: `drover_sentinel_hosts` derives API addresses from `groups['valkey']` and `valkey_sentinel_port`; `drover_sentinel_master_name` uses `valkey_sentinel_monitor_name`. Both API and Worker read these existing `[cache]` Settings. The data Redis URL retains its DB index (default 7), password-file authentication and TLS/query options; Sentinel discovery does not receive the data password. For an external standalone Redis, set `drover_sentinel_enabled: false` explicitly. Readiness PING is not a write-capability test: qualify callback creation/one-time consumption and DB isolation using owned expiring keys, never force failover of shared Valkey merely for Drover acceptance.

## Execution-authority cutover qualification

**Not live-verified.** OpenSpec tasks 4.3/4.4 are complete with local evidence only (2026-10-07: non-integration suite 1123 passed / 1 skipped, SDK proxy 114 passed, real-SDK loopback trust test, disposable MariaDB 11.4 ledger 001–004). Existing lifecycle tests and that local evidence are not acceptance evidence for the new trust/guest-rollout behavior on a real cloud.

- Apply manifest migration `004_execution_authority.sql`, drain pre-upgrade mutation/`WAITING_CALLBACK`/HA/agent jobs with the old worker, then cut over API and Worker together. Legacy jobs do not gain a delegation automatically and the new worker rejects missing delegation. Reauthorize legacy ACTIVE clusters and confirm operation success/guest rollout before removing `afterglow-cluster-mgr-*` users or old app credentials out of band. Follow the [ordered migration runbook](../../drover/migrations/README.md#execution-authority-upgrade-004); do not use this manual gate to improvise a production cutover.
- Kolla renders `operation_trust_ttl_seconds`, `operation_trust_min_remaining_seconds`, `delegated_required_roles`, `delegated_optional_roles`, `guest_rollout_timeout_seconds` from the `drover_`-prefixed variables. Defaults are 14400s, 300s, `["member"]`, `["load-balancer_member"]`, 600s. Runtime bounds are TTL 900–86400s, minimum remaining 60–3600s and less than TTL, rollout 60–3600s; required roles cannot be empty. Runtime and Kolla reject `admin`/`manager` role configuration; optional roles are only delegated when held. Barbican member/Octavia member-role sufficiency is **[INFERENCE]**, requiring deployed policy/ACL qualification.
- Remove Settings/Kolla `drover_afterglow_provisioning_url`, `drover_afterglow_provisioning_token`, `drover_afterglow_provisioning_token_file` and environment `DROVER_AFTERGLOW_PROVISIONING_TOKEN_FILE`. Provisioning intents are removed; Kolla removes the old `afterglow_k3s_provisioning_token` file. GPU admission settings and token file remain; each new native GPU worker create re-checks configured admission and performs Nova/Cinder work in Drover, not Afterglow.
- Before claiming acceptance, exercise requester impersonation/scope/least-held-role/expiry verification, terminal revocation versus transient retry, callback trust continuation, idle release and trust DELETE/sweep with no fallback. After each job, released/revoked trusts are deleted through their own impersonating trust-scoped password token with no project selector; success/404 records `deleted`, Unauthorized/Forbidden leaves the row released/revoked with `trust inert until expiry`, and outages retry on the 300s sweep. Expired rows require Keystone GET 404 before `expired` is recorded. [Keystone master trusts.py](https://github.com/openstack/keystone/blob/master/keystone/api/trusts.py) `_check_delegated_token` does not block ordinary trust-scoped tokens; `identity:delete_trust` allows the trustor represented by an impersonating token. [Master users.py](https://github.com/openstack/keystone/blob/master/keystone/api/users.py) still blocks trust/OAuth/EC2 app-credential management and restricted app credentials from managing additional credentials, so app-credential revocation requires the owner's non-delegated token. `tests/test_native_trust_loopback.py` defines real keystoneauth1/keystoneclient HTTP create/authenticate/delete against a synthetic loopback provider and revoked-role denial; that is test-defined, not evidence this documentation slice ran it or a live cloud passed.
- Qualify separate restricted user-owned control/guest credentials. Stampede revalidates owner scale capability; reconcile/health revalidate get. Test creator departure and deletion by a different authorized actor, secret erasure and owner-revocation backlog, plus legacy reauthorization/Stampede enable rejection without control authority. Tenant `DELETE` is durable; current tenant `delete-async` runs on the caller connection and has no durable disconnect guarantee.
- For guest reauthorization, verify `cloud-config`/`manila-cloud-secret` Secret and Octavia Ingress ConfigMap key replacement, kube-system consumer restart **and completed rollout**, control-plane host Jobs using `nsenter` to rewrite `/etc/kubernetes/barbican-cloud.conf` and existing `cloud.conf`, `barbican-kms.service` restart/socket readiness, and the final Secret-write probe. Only then may staged credentials activate and old secrets retire. Inject partial failures and confirm old active credentials remain valid; do not assume already changed guest objects are automatically rolled back. Owner retire uses the owner's normal token; other-owner/legacy credentials remain a reported operator responsibility.

These are required qualification checks, not a statement that the current manual workflow already executes them. Keep synthetic HTTP/Keystone/Kubernetes smoke, migration-ledger results, container/image checks and live cloud acceptance separate; never record secret values in evidence.
